# 建筑规范 AI 知识库 — 实施方案

## Context

公司有一批建筑设计规范（国标 GB/GBT、行标 SH/JGJ、中石化企标 DEP-*、国际 IBC/NFPA），
目前只能靠人工翻 PDF 查条文。目标是做成微信扫码即可访问的问答系统，让设计人员直接提问、
拿到带出处的条文答案。

### 现状勘察结论（已实测）

工作目录 `<知识库目录>/`：

| 项 | 实测结果 |
|---|---|
| 文件量 | 初勘 76 PDF + 60 Word；`建筑规范/标准库/` 并入后台账共 **329 份**，其中 250 份为扫描件 |
| 已有原型 | `建筑法规知识库/knowledge-base/`，约 2000 行 Python |
| 原型状态 | **从未跑通** — `parsed_text/`、`cleaned_text/`、`chroma_db/` 三个产物目录全空，README 中的问答示例是虚构的 |
| MinerU 产物 | `建筑法规知识库/MinerU/` 下 32 份有效解析结果，质量可用 |

**发现一：核心规范全是扫描件。** GB/SH 类 17 本中 13 本为纯图片 PDF（GB 50016、GB 50160、
GB 50011、GB 51251、GB 55037、SHT 3006 等，三页抽样可提取字符数为 0–12）。OCR 是必经路径。

**发现二：MinerU 输出可用。** 条文号完整保留（如 `5.5.17`），表格转为 HTML，
`*_content_list.json` 含 `page_idx` 字段 → 引用可定位到 PDF 具体页。

**发现三（关键风险）：同一条号在一个文件里出现两次，内容不同。**
`GB 50016-2014 建筑设计防火规范(2018版)` 的 `full.md`：第 1–253 行是「2018 年局部修订条文」，
第 254 行起才是 2014 年原版正文。条号 `5.1.3A`、`5.5.8` 等各出现两次 —— 前者是现行有效版本，
后者是**已被替换的旧版**。按字数机械切块入库，AI 约有一半概率引用作废条文。
`GBT 50378（含条文说明）` 同理：条文说明会把条号再重复一遍，且不具强制力。

**发现四：强条标记在 OCR 后丢失。** 规范正文写明「以黑体字标志的条文为强制性条文」，
但 MinerU 输出的 Markdown 无粗体信息，该标记已不可恢复。

**发现五：表格 OCR 有破损。** GB 50016 中出现 `2&lt;v&gt;` 破损单元格与游离 `</v>` 标签。
而防火间距表、疏散距离表正是查询频次最高的内容。

**发现六：文件层面的问题。**
- `GB_T 50779-2022`（19MB）、`JGJ_T 473-2019`（31MB）为加密/DRM 格式，非标准 PDF，无法解析，需重新获取
- 疑似重复：`GB 50016-2014...(2018版).pdf`（37MB）与 `建筑设计防火规范.pdf`（0.9MB）
- MinerU 目录中 `NFPA 5000` 重复解析 4 次，`IBC` 被拆为 1/2/3/4 册

### 数据源决策（2026-09-21 实测修订，推翻原方案）

原计划以 MinerU 的 Markdown 为正文来源。实测 10 本后**改为 Word 为主、MinerU 只供页码**：

| | Word（.docx） | MinerU（PDF→MD） |
|---|---|---|
| 条文号 | 无错 | 偶有 OCR 错位 |
| 表格数值 | `<w:tc>` + gridSpan 可精确还原 | 有 `2&lt;v&gt;` 类破损 |
| 强条声明 | 条文说明里明文「本条为强制性条文」 | 同左，但受 OCR 质量影响 |
| 页码 | **无** | `page_idx` 精确 |

两边条文号对齐率实测 **100%（473/473）**，所以可以用条号做连接键：
文本取 Word，页码从 MinerU 查回来。发现四、五的影响因此大幅降低——
强条改从条文说明的文字声明中提取（见下），表格改从 Word XML 还原。

**发现七：Word 把带单位的数值写成了 OMML 公式。** `<m:oMath><m:t>32</m:t><m:t>m</m:t>`，
`python-docx` 的 `.text` 只读 `<w:t>`，实测 GB 50016 有 **46%（214/466）** 的条文
因此丢掉关键数值（「高度不宜大于　，不应大于　」）。连 `<m:t>` 一起取后归零。

**发现九：Word 表格的合并列信息不完整。** 转换器常常不写 `gridSpan`。
表 5.5.17「歌舞娱乐放映游艺场所」原本横跨 3 个名称列，Word 里只占 1 列，
又凭空补了一个「—」凑满 9 格——**数值本身没错，但落到了错误的列下面**。
切条器如实还原源文件（不猜着修），由 `tools/review.py` 把这类行标黄给人核。
28 本合计 **48 行**需人工确认，工作量可控。

判据是「行末连续数值格多于众数」，但**打勾矩阵不适用**：GB 50453 的
「甲|乙|丙|丁」分类表里，行末破折号的个数表示★打在第几列，本来就该逐行不同，
按这个判据 23 行的表能标出 10 行，全库多出 128 行假警报。
校对页的全部价值就在于标黄的行值得人去看，假警报会直接让人不再信这个颜色，
故对含打勾格的表整表跳过判定。

**发现八：修订条文是干净的最终态。** Word 丢失了下划线/删除线标记，原本担心
无法区分「新增」与「删除」。逐条比对 19 条重叠条文，**0 条**存在实质性删除内容，
故程序可直接「有修订版就用修订版」，无需人工誊抄。

**发现十（接入企标时才暴露）：企标按 GB/T 1.1 编写，条文号根本不在文字里。**
国标/行标用工程建设标准写法，条文号是正文的一部分；中石化企标 `DEP-*` 用 Word
的自动编号（`w:numPr`），`python-docx` 读到的正文**一个数字都没有**。
13 本企标里有 3 本游离率 100%。这不是排版差异，是两套编写规则，必须另走一条
解析路径（见 1.3b）。**凡是新接入一类来源，都要先确认条文号从哪来，再谈切条。**

**发现十一：企标在 MinerU 里零覆盖，页码要另想办法。** 页码是核对原文的唯一入口，
没页码的答案等于不可核对。改为直接从 PDF 文本层按条文顺序单向反查（见 1.3c）。

**发现十二：转换工具把比较号转义了两次。** 正文里留着 `&lt;` `&gt;` 字面量
（「塔高H&lt;80m」「FP&gt;50m²」）——XML 解析器本来就会还原实体，还留着说明
源文件里就是这四个字符。全库 431 处，都是限值的比较号，已在取文本时还原。

### 已确认的决策

- 一期范围：原定 10 本高频规范；实际凡有 Word 源的都能切通，已扩到 28 本
  （含 13 本企标）。仍是本地验证，暂不上线
- 数据合规：**2026-09-21 信息中心答复——企业标准（DEP-*）可以走公有云 API**。
  可替换层 `src/providers.py` 保留，理由从「合规闸门」变成「答复可能改；
  且只有一个地方出网，出事只查一个文件」
- 微信形态：普通 H5 + 访问口令（二维码指向网页，微信内置浏览器打开）
- 规模预期：按最终约 260 本设计，但不为此提前过度工程

### 选型说明（与初步建议的差异）

初步建议过 RAGFlow。确定一期为「本地验证 + 自建 H5」后收回该建议：
RAGFlow 镜像 19GB、内存 16G 起步，而它解决的是存储与检索运维，**恰好不解决本项目的两个
核心风险（切条质量、作废条文）**，且其内置分块器无法处理「修订条文优先」逻辑，
仍需通过 API 灌入自行切好的 chunk。一期用轻量栈（2 万 chunks 量级完全够用），
把框架决策推迟到阶段 3 规模铺开时。

## 阶段 0 — 汇总与台账  ✅ 脚本已完成，status 列待人工填写

**这一步决定系统能不能用，不能跳过。**

```bash
python -m src.catalog --roots ../建筑规范 --out data/catalog.csv
```

扫描范围只取 `建筑规范/`。**不要扫父目录**——`MinerU/` 下是解析中间产物
（`*_origin.pdf` 副本、机器翻译的 docx），扫进来会凭空多出 50 多行假规范；
`knowledge-base/` 是上一版原型，同理排除。

每行一本规范：

```
file_path, std_code, std_name, version_year, status, superseded_by,
category, has_clause_notes, is_scanned, page_count, sha256, dup_group, issue, note
```

- `status`：现行 / 废止 / 被代替 — **必填**，错一个就可能让人按废止规范做设计
- `category`：国标 / 行标 / 企标 / 国际
- `is_scanned` 由脚本判定（抽样页可提取字符数 < 300 即为扫描件）。
  只看首页不可靠——规范封面往往是图片而正文有文本层，故取全书 1/4、1/2、3/4 三处抽样
- `dup_group`：同 SHA256 的文件共用一个组号；`issue`：DRM 加密、打不开等

脚本自动填 `file_path / is_scanned / page_count / sha256 / dup_group / issue`，
从文件名正则抽 `std_code`；`status` 与 `superseded_by` **必须人工核对**
（住建部标准公告 / 工程建设标准化信息网）。

规范名从文件名剥编号得来，会出现在**每一条引用**里，所以剥的时候两个坑：
括号不能连着分隔符一起剥（「建筑设计防火规范(2018版)」会剩「…(2018版」），
网页导出的 Word 用 `+` 当分隔符（「建筑抗震设计规范+(附2016年局部修订)」）。

**实测**：329 份 / 250 扫描件 / 11 个重复组 / 33 个编号未识别 / 3 个打不开。

**交付**：`catalog.csv`，人工逐行确认过 status 字段。

### 1.3 切条器 `src/chunker.py` — 项目胜负手  ✅ 已完成

输入 Word（正文）+ `*_content_list.json`（页码），输出 chunk JSONL。

**分区识别**（先做这步，再切条）：
将文档切成 `局部修订 / 正文 / 条文说明 / 前置(目次·前言·公告)` 四类区段，
前置区段整体丢弃。排版差异极大，实测不能靠「文档以什么开头」判断：

- 分区锚点取**最后一个**「条文说明」标题。GB 50011 有两个（第一个属局部修订部分），
  取第一个会把全书正文吞进条文说明区（实测检索池只剩 10 条）
- 标题写法不一：GB 50011 是「条文说明」，GB 55015 是「四、条文说明」
- 正文起点不能取「最后一个第 1 章锚点」，改用**与排版无关的判据**：
  正文一定是条文最密集的一段，取条文行数最多的区间起点

**条文切分**（每条规则都是被真实数据逼出来的）：
- 条文号恒为三级。所有二级编号实测均为垃圾——目次行「5.4 平面布置 (67)」、
  公式残片「0.58倍;」。放行二级编号会往检索池注入 242 条假条文
- 负向断言排除三类误命中：`条`（交叉引用残片「6.2.5条的规定」）、
  `.`/数字（阻止回溯，否则「12.2.4条」退一步匹配成「12.2」）、
  `、`/`，`（公告里的作废条文清单「4.2.3、4.2.5、4.2.8…」）
- **款行与章标题字面上无法区分**（「1 同一结构单元的基础不宜设置在性质截然不同的
  地基上。」只有 25 字）。靠编号序列区分：章号必递增，款号每条重新从 1 数起。
  不加这条判据时 GB 50011 正文有 **23%** 的文字被甩出条文之外
- 悬空引用续行：「……应按本规范第」断行后的「5.1.5 条确定,…」不是新条文
- 附录单独处理：条号形如 `A.0.1`；无编号的附录（GB 51251 整篇就是一张表）
  以「附录A」为条号建块，否则那些表会挂到上一章的末条上
- 一个 chunk = 条文号 + 条文正文 + 下属款项 + 随附表格 + 注
- **表格必须跟着所属条文走，不单独成块**（表 5.5.17 脱离 5.5.17 条就没有意义）
- 表格转 Markdown 必须读原始 `<w:tc>` + gridSpan/vMerge。
  按「相邻文本相同就去重」消合并列会把表 5.5.17 的「9 | — | —」压成「9 | —」，
  **直接改变规范数值**

**质量指标：正文游离率。** 不属于任何条文的正文字数占比，
28 本现均为 **0.0%**。这个数一旦回升就说明切条规则漏了新的排版形态。

**chunk metadata**：
```
std_code, std_name, version, clause_no, chapter_path, page_idx,
section_type,    # 正文 | 条文说明 | 修订
is_mandatory,    # 见 1.5
status,          # 继承自 catalog
superseded       # 见下
```

**修订优先去重（针对发现三）**：
同一 `std_code + clause_no` 下，若存在 `section_type=修订` 的 chunk，
则把 `section_type=正文` 的同号 chunk 标记 `superseded=true`，**排除出检索池**。
`section_type=条文说明` 的 chunk 单独建池，仅在用户追问「为什么」时才检索，
且回答中必须标注「以下为条文说明，不具强制力」。

### 1.3b 企标（DEP-*）另走一条解析路径 `src/depdoc.py`  ✅ 已完成

把 13 本企标接进来时，上面那套规则**整体失效**——3 本游离率 100%。
原因不是排版差异，是两套标准编写规则：

- 国标/行标按工程建设标准写法，条文号**印在正文里**，`python-docx` 读得到；
- 企标按 **GB/T 1.1** 写，编号是 Word 的**自动编号**（`w:numPr`），
  正文文字里一个数字都没有。`python-docx` 的 `.text` 天然看不见。

第一版想从 `numPr` 反推层级，结果章数虚高（20/13/41 章 vs 实际 11/6/9）——
次级 numId 的 `ilvl` 会从 0 重新起算。**改为以「目次」为准**：

- 章号是从目次**取**的，不是数出来的。因此漏认一章只会让那章的内容并入上一章，
  **不会让其余章号整体错位**——损害是局部且有界的。
- 所以可信判据取**顺序单调**（匹配到的标题在目次中的次序递增），不取「认全」。
  不单调说明匹配到的根本不是章标题，那才是全书编号作废。
- 目次与正文的标题常差一个标点（目次「变配电类建筑物功能概述」，
  正文「变、配电类建筑物功能概述」），比对前连标点一起归一化。
- `trusted=false` 时**整本清空 `clause_no`**。引用里写错条号，比不写条号危害大得多。

**路径选择不靠特征猜，靠跑两遍比**：国标路径的游离率 > 5% 或章号错位超过阈值，
就再跑一遍企标路径，仅当后者 `trusted` 且文字量 ≥ 前者 90% 时采纳。
（AR2106 实测：企标路径 45 条/6232 字全对，国标路径 37 条/6759 字但 34 条章号是错的。
字多不等于对——这个门槛放宽到 0.9 就是为了让「更少但更对」能赢。）

### 1.3c 两个补丁：页码兜底与章节路径自查  ✅ 已完成

**页码**：企标在 `MinerU/` 下零覆盖，13 本全无页码，而页码是核对原文的唯一入口。
`src/pagefind.py` 改从 PDF 文本层反查：每条取一小段做探针，**按条文顺序单向前搜**
页文本。单向是关键——「本标准适用于……」这类套话不单向搜必然命中前言。
实测 **751 条精确命中、0 条搜错**，另有 127 条沿用上一条的页码（同页多条是常态）。
全库现在只剩 GB 50011 的 A.0.31 一条没有页码。

**事后反查验证**（拿切好的条文回 PDF 对页，不是复用定位时的探针）：
886 条企标正文中，**791 条在标注页上原样找到**，2 条在邻页，21 条全书都找不到，
72 条因条文太短无法构成探针。那 21 条「全书找不到」是探针跨了标题与正文的接缝
（「建筑结构形式的选择」+「一般情况下，…」在 PDF 里本就不相邻），
**全书都搜不到恰恰说明不是页码错**，而是这个串在原文里不存在。
即：可验证的部分里**没有一条页码是错的**。

**章节路径**：章标题和条文款行字面上仍会混。原先用「标题不超过 16 字」的长度上限，
这是**错的**——那个统计量是在已经切坏的数据上量的，像 GB 50016 第 4 章
「甲、乙、丙类液体、气体储罐（区）与可燃材料堆场」（22 字带括号）从来没被认出来过，
自然也就没进过样本。改成结构自校验 `confirms()`：候选标题编号必须与其后条文号
**不相冲突**（不得倒退），窗口内找不到条文号则视为无反证、放行。
再加一道 `repair_chapter_paths()` 事后比对 `chapter_path` 与条号是否一致，
不一致就用同章内自洽的样本重建；没有自洽样本时**拒绝猜**，留空。
章号不符：240 → **25/5589（0.45%）**，其中 22 条在条文说明区（不在检索池），
实际在池内的只剩 3 条。

### 1.6 索引与检索 `src/index.py` / `src/retrieve.py`  ✅ 已完成（09-23 向量索引已建好，7,678 条）

- 向量：bge-m3 → Chroma
- 关键词：jieba 分词 → rank_bm25
- 融合：RRF（Reciprocal Rank Fusion）
- 重排：bge-reranker-v2-m3，取 top 8

**查询预处理是重点**：用正则先识别查询里的规范编号（`GB\s*\d{5}`）和条文号（`\d+\.\d+\.\d+`）。
命中则直接走 metadata 精确过滤，**不依赖语义检索** —— 用户输入 "GB 50016 5.5.17" 时，
纯向量检索几乎必然失败。

检索时默认过滤：`superseded=true`、`status=废止`、`section_type=条文说明`。

补充两点实现结论：

- **条号命中即终止**。查询里识别出条文号就只返回精确结果，不再掺语义结果——
  答案是确定的，掺进来只会引入噪音。
- **规范名也要能当过滤条件**。同事张口说的是「建筑抗震设计规范 5.1.4」，
  不是「GB 50011 5.1.4」。只认编号的话，条号直达会把全库所有 5.1.4 一起端上来，
  排第一的是企标 AR2106。名字后缀（「(附2016年局部修订)」）允许省略；
  两本规范重名就谁都不认——**引错规范比认不出规范危害大**。
- 限定了规范之后，**必须在那本里重新排名次**，不能「取全库前 30 再过滤」。
  否则「建筑设计技术规定里卫生间的做法」会因为那本一条都没挤进前 30 而颗粒无收。
- 送进 embedding 的文本必须带**规范名 + 章节路径**前缀。条文正文常只写
  「不应小于表 5.2.2 的规定」，「防火间距」四个字只在节标题上；不带前缀，
  这一条在语义空间里几乎没有信息。
- 索引按内容 SHA1 增量重建。切条器改一次就全量重算 embedding，迭代会很难受。

**无 API key 时自动退回纯 BM25**，功能不中断，界面上明示当前是关键词检索。
实测纯 BM25 已经可用：「厂房内疏散楼梯的最小净宽度」→ GB 50016 3.7.5 排第一；
「控制室抗爆设计有什么要求」→ DEP-T-AR2001 6.2 + GB 50160 5.7.1A + SH/T 3006 4.1.4。


SSE 事件四种：`hits`（检索结果，先出，不等模型）、`delta`（生成的字）、
`nollm`（没配 key，页面转为纯检索模式）、`error`。**先出条文后出作答**是有意的——
模型挂了、key 没配、网络不通，用户至少还拿到条文原文和页码，系统不会整个白屏。

### 与原计划的三处偏离（都是有意的）

| 原计划 | 实际 | 为什么 |
|---|---|---|
| JWT | HMAC 签名票（到期时间 + 签名） | 不需要 JWT 的任何一个特性。没有用户、没有声明、没有第三方要验。一个 `exp.sig` 就够，还省一个依赖 |
| token 存 localStorage | httponly cookie | localStorage 的 token 任何一段 JS 都能读走。httponly 读不到，XSS 拿不到票 |
| 全量问答日志落库 | 不落库 | 「谁在什么时候查了什么」是个人信息。一旦开始存，就要隐私政策、告知同意、留存期限那一整套。查规范不需要知道是谁在查。要发现检索失败 case，用 1.8 的人工验收集，不用偷偷记 |

口令只从 `KB_PASSCODE` 环境变量读，**代码里没有也不会有默认值**——
带默认口令的内部系统等于没有口令，而这种默认值最后总会跟着代码一起上线。
本机试跑用 `KB_DEV=1`：每次启动现随机生成一个口令打在日志里，只绑回环地址。

`KB_SECRET` 不设就每次启动现生成，即重启会让所有已发出的票失效。
这是有意的——口令万一外传，重启一次就全作废。

- **AI 解读按最小一套 Markdown 渲染**（加粗、列表、小标题），先整体转义再套标签。
  模型写的出处 `[GB 50016 第5.5.17条 P38]` 变成可点的链接，点了滚到对应条文卡并闪一下——
  AI 说的每一句都能立刻对到原文，这是那段话能放在页面上的前提。
  模型常省略年份，卡片按规范号前缀匹配
- **每批结果先说明来路**：「按条号直达」是确定的，「关键词检索」是「像」，可信度不同，
  不该长得一样。带上解析出的限定（限定 GB 50016 / 只看强条）
- **SSE 改用 `fetch` 读**而不是 `EventSource`：能看到 401（口令过期要回登录页，
  而不是报「出错了」）、能中途停（查按钮变「停」）、能加参数。协议没变
- **「AI 解读」开关**记在本机；关掉或点「多显示几条」（k=20）时走 `llm=0`。
  查条号的人本来就不需要模型开口，省一次调用也省几秒
- **在库清单**：按 GB / GB/T / SH / 企标分组，可筛选，点一本把规范号填进问题框
  （问题里带规范号就只在这本里查）。同事的第一个问题往往是「有没有 GB 50016」
- **最近查过**：最多 8 条，只存这台手机的 localStorage，不上传——服务器端仍然什么都不记
- **复制引用**：出处 + 原文一起进剪贴板，贴到设计说明里用。http 下没有剪贴板 API，退回 `execCommand`
- 退出按钮；`format-detection=telephone=no`，否则 iOS 会把「50016」当电话号码

前端联调不用真后端：`python -m tools.ui_mock` 起一个只绑回环的假后端，
条文是真的（BM25 查本机语料），AI 那段是照命中拼的假话慢慢吐。

### 2.1 回答与原文对照

模型说的每一句都要能落回原文，否则这段话不如不显示。两层：

**出处可点**。回答里的 `[GB 55037-2022 第7.1.5条 P38]` 渲染成链接，点了滚到对应
条文卡并闪一下。模型常省年份，卡片按规范号前缀匹配。

**引用了哪几条要说清楚**。检索给 8 条，模型实际用上的可能只有 3 条，其余 5 条是干扰。
被引用的卡片左边加一道竖线，上方一行「检索到 8 条，AI 引用了其中 3 条」，
外加「只看被引用的」开关。

反过来更重要：**模型引了检索结果里没有的条号，要当场报出来**——
那是它编的。这种句子看起来和真的一模一样，只有跟检索结果比对才发现得了。
页面上显示「另有 N 处出处不在结果里，需核对」，点那个出处则提示「这条不在本次检索结果里」。

### 2.2 跳到原文 PDF 的对应位置

条文卡上「看原文 P38」→ 把原件那一页渲成灰度 JPEG 发过去。

**为什么是图片不是 PDF**：手机上的 PDF 阅读器不认 `#page=38`，微信内置浏览器
更是要先把整本下下来（GB 50016 那本 35 MB、GB 55037 那本 63 MB），
而同事只想看这一页长什么样。一页 JPEG 八十到二百 KB，哪儿都打得开。
渲染倍率 1.6（≈115 dpi），手机上看清五号字够用。
「整本」按钮留给电脑——浏览器自带阅读器认 `#page=`，能直接翻过去。
翻页、放大、上一页下一页都在这个查看器里，不用离开页面。

**页码指的是哪一本，靠 `src/source_pdf.py` 算**。这是唯一容易出大错的地方：
同一本规范在台账里常有好几个 PDF（整本一个、分卷五个），
`chunk.page_idx` 是切条时按某一个特定文件数出来的，指错文件，
「第 38 页」就是另一本的第 38 页——**比没有页码更糟，因为它看起来是对的**。
所以 `resolve()` 的判定顺序直接照抄 `batch.main()`，索引函数也是从 `batch` import 的，
两边不可能算出不一样的结果：

| 切条来源 | 页码对应的 PDF |
|---|---|
| Word + MinerU 页码 | `../MinerU/<文件名>.pdf-<hash>/` 对应的那本，即台账里同名 PDF |
| 本地 OCR | `data/ocr/_merged/<书名>.pdf`（分卷合并过的），没合并过则台账同名文件 |
| 企标 Word + 正文定位 | 台账里该编号的第一个 PDF |

`python -m src.source_pdf` 逐本核对，**35 本全部对得上**（最大页码 ≤ 全书页数）。

另外抽查了 85 条有文本层的条文，按正文前 25 字在不在那一页上判断：
**81 条正确**，4 条对不上——都是 DEP 企标，且那几条的正文在 PDF 里**整本都搜不到**
（Word 版和 PDF 版内容不一致），属于切条阶段的已知偏差，不是这次定位的问题。
另外核实了一次 0 与 1 的差：`page_idx=38` 的 GB 50016 第3.2.2条，
渲出来的第 39 页上印的正是「3.2.2 高层厂房……」，接口 `page_idx + 1` 没错。

渲好的页缓存在 `data/cache/pages/<归一编号>/<页>.jpg`，一页平均 191 KB。
全库都翻遍约 760 MB，删掉会自己重建。规范号只当缓存目录名和 dict 的键，
**不拼进任何路径**——`?code=../../etc/passwd` 走的是「查不到这本」那条路，返回 404。
服务器上没带原件目录时接口返回「这本规范没有可用的 PDF 原件」，页面照常能用，
只是没有「看原文」。

本机实测（`tools/ui_mock.py` + 375×812）：35 本各取自己最大的那个页码请求一次，
全部 200；越界页、不存在的规范号、路径穿越都是 404；翻页/放大/整本链接/
首末页按钮禁用/口令过期回登录页/编造出处提示，逐条点过。

### 3.1 本地 OCR `src/ocr.py`  ✅ 已打通

**不花 token。** magic-pdf / MinerU 是本地模型，成本只有机时和电费。
只有 embedding（bge-m3，当前免费）和问答时的 DeepSeek 调用才计费。

踩过的四个坑，都写在代码注释里：

1. **PyTorch 2.6 起 `torch.load` 默认 `weights_only=True`**，doclayout_yolo 的权重
   直接抛 `UnpicklingError`。按类名 `add_safe_globals([YOLOv10DetectionModel])` 放行，
   比全局关掉窄。这条决定了必须走 Python API，命令行 `magic-pdf` 用不了
2. **模型仓库把检测模型换成了 v5，magic-pdf 1.3.12 的配置还指着 v3**，v3 那份已下不到。
   检测网络结构是从权重文件里读出来的（`get_arch_config`），换文件即可；
   `_patch_ocr_det()` 只在配置指定的文件确实不存在时才替换，上游修好后自动失效
3. **scipy 1.15.3 的 PROPACK 二进制在 macOS 26 上加载不了**（`__thread_bss` 段格式），
   连带 sklearn 整个进不来。降到 1.14.1 解决
4. **出版社的绿色印章是最大的质量杀手**——见 3.2

配置从 `~/magic-pdf.json` 挪进了仓库 `kb/conf/magic-pdf.json`（`MINERU_TOOLS_CONFIG_JSON`
支持绝对路径）：device-mode、要不要跑公式模型这些参数直接决定入库文本长什么样，
属于工程的一部分，不该藏在某台机器的 home 目录里。

`device-mode: mps` 比 cpu 快 27%（14.4 → 10.5 s/页），而且 CPU 模式会被自动降级成
`ch_lite` 轻量识别模型，MPS 模式用的是 `ch_PP-OCRv4_rec_server_doc`——**又快又准**。

### 3.1b 一页 10 秒到底耗在哪 — 量了才敢调

一页 10 秒、剩一万二千页就是 37 小时，值得花半小时测一遍再动手
（`tools/ocrbench.py` 是当时写的对比工具，留着复用）。

按阶段拆开（GB 50763 无障碍设计规范，6 页，MPS）：

| 阶段 | 原 | 调整后 | 说明 |
|---|---|---|---|
| 文字识别 rec | 4.85 s/页 | **2.18** | 批大小 6 → 32 |
| 文字检测 det | 3.34 s/页 | 3.34 | 按版面区域逐块检测，一页调 15 次 |
| 版面检测 | 0.73 s/页 | 0.73 | 已是最快的 doclayout_yolo |
| 公式识别 | 关 | 关 | 规范里没有 LaTeX |
| **整页** | **12.12** | **10.11** | **约 1.2×** |

**为什么批大小 6 在这台机器上是错的**：MinerU 的默认值照 CUDA 定，
MPS 上每次前向都要过一遍 GPU 调度。一页规范四五十行字，按 6 一批就是八九次调度，
时间几乎全花在来回上。改成 32 之后识别这段快了一倍多。

改批大小会改变同批图片的补白宽度，理论上可能影响识别结果，所以**逐字比对过**：
4616 字里两处不同，一处是分号全角半角，另一处批 32 反而是对的
（「无障碍**出入口**」，批 6 认成了「出**人**口」）。没有变差。

**试过并否掉的两条**：

- *换更轻的识别模型*。v5 server 比当前的 v4 server_doc 只快 1.17×、v5 mobile 快 1.03×；
  而批大小改完之后识别只占两成，换模型最多再省 5%。
  识别错一个数字就是错一条限值，为 5% 冒这个险不值。
- *开两个进程并行*。两边都掉到 20 s/页以上，合起来跟单进程一样快，交换区还顶到 22 GB。
  **瓶颈是 GPU 和内存，不是 CPU**——全程只用了十核里的一核，加进程只会互相抢。

det 那 3.3 秒是 MinerU 按区域逐块检测的设计代价。改成整页一次检测要动它的流程，
识别结果会变，为了 1.3 倍不值得在一个要当法规依据用的库上冒这个险。

**第三条也否掉了：降渲染分辨率**。200 → 150 dpi 直觉上该快，实测两头都更差：

| | s/页（两轮交错） | 文本 |
|---|---|---|
| 200 dpi | 7.55 / 6.31 | 基准 |
| 150 dpi | 9.16 / 7.86 | **52 行不同** |

不只是慢，是认错了：「贵宾」→「责宾」，行尾冒出「达 一」「C」「Y」这类把噪点
当字的垃圾。原因是检测器把每块长边压到 960 且**只缩不放**，降到 150 之后字相对
这个上限更小、边缘更糊，检测框反而更碎。

> 这条的第一次测量是错的，记下来当教训：我最初改的是
> `magic_pdf.data.utils.load_images_from_pdf`，那个函数只给语种检测用，
> 真正的渲染路径是 `dataset.py:346 → fitz_doc_to_image`。补丁没生效，
> 于是量出「快 1.6 倍、文本一模一样」——**「文本一模一样」正是补丁没打上的特征**，
> 改了渲染分辨率不可能一个字都不变。换对地方、交错跑两轮、
> 顺便打印像素数（1,657,126 vs 932,044）确认补丁真打上了，才是上表的结果。

另外确认了一条无需优化的：`det_limit_type` 本来就是 `max`，小区域裁图不会被拉大，
那里没有浪费。

**结论：本地天花板就是 10 s/页。** 四条路试完只有批大小那条有用。

### 3.1c 二三档改走云端 `tools/ocr_cloud.py`

本地跑到头是 10 s/页，二三档还剩一万多页 = 约 30 小时，而且这台 16G 机器扛不住：
`logs/ocr_t1.log` 里第 6 本掉到 **45.2 s/页**，当时交换区 21.5G/22.5G、
负载 180、累计换页 5900 万次。`_reclaim()` 只能压住单进程的增长，压不住整机。

于是二三档交给 **MinerU 官方云端 API**，一档继续在本地跑完。选它的理由按重要性排：

1. **产物格式相同**。返回的 zip 里有 `**_content_list.json`，跟本地产物同一个 schema，
   `chunker.py` 一行不用改，也不用重新验证切条逻辑。换任何别家都要重做这步验证。
2. 免费，每天 1000 页最高优先级；超出的部分降优先级排队，不拒绝。
3. 有 `vlm` 模型可选，比本地这套 pipeline 新。

**保密**：二三档队列是 GB 国标 / JGJ 行标 / SH 行标——书店买得到的公开出版物，
外加 3 个 Q/SH 企标共 54 页。DEP 企标那 13 本有文本层，早就走 `depdoc.py` 切完了，
根本不在 OCR 队列里。企标出公网也已获准（2026-09-21 信息中心答复）。
即便如此，`_preview()` 每次提交前仍按标准类别列一遍清单再等回车——
「获准」和「知道自己发了什么」是两回事。

**工程要点**（都是会出错、所以写成代码而不是靠记性的地方）：

- **去水印仍在本地做**。3.2 那个绿印章是输入污染，换谁识别都一样吞字，不能指望云端。
- **超 200 页要切段，切了就得把页码接回去**。`chunker.py:527` 直接读
  `b["page_idx"]` 且无默认值，段内页码都从 0 重数，不加偏移量的话
  533 页的 GB 50017 会有三段都自称第 1 页，条文出处就指错地方。
  超限的一共 8 本，全在三档：GB 50017(533) / 50074(384) / 50015(294) /
  50156(251) / JGJ-T 14(240) / GB 50025(219) / 50003(205) / 50229(203)。
- **先落盘 batch_id 再上传**。反过来写的话，传到第 30 个断网，batch_id 就丢了，
  那 29 个已上传的既查不到状态也取不回来，重跑还会再传一遍。
- **切段文件名带页区间**。字节数超限时会把每段页数减半重切，
  只按段号缓存的话第 0 段会复用上一轮那个更长的文件，页数跟台账对不上。
- 进度记在 `data/ocr/_cloud/manifest.json`，可中断可续跑，
  已在云端排队的不会重复提交。

出网的文件因此有两个：`src/providers.py`（向量/重排/作答）和这个。
两边的文件头都写明了为什么出网、出什么，要审就看这两个。

### 3.1d 一档重启之后：45 s/页的根子找到了，是去水印那步

09-21 深夜按待办 11 重启一档，接连撞上四件事，都记下来，因为每件都有个
「下次别再犯」的结论。

**一、`nohup` 起的进程随会话一起死了**（23:49，日志无任何报错，就是没了）。
以后长活一律在**你自己的终端标签页**里起，命令见待办 11。现在那个在标签页「一档 OCR」里。

**二、重启六分钟没有任何输出**。「已有产物就跳过」的判断写在 `run_one()` 里，
而 `merge` / `preclean` 在它前面——已跑完的 14 本每次重启都要按扫描分辨率
整本重渲一遍去水印，渲完才发现早跑完了，一千页白渲。判断挪到循环最前面，
现在 14 本几秒钟跳完。

**三、GB 50984 那本「不用去水印」的结论算了 34 分钟，没存**。161 页按 400dpi
渲完发现没盖章，直接扔掉，下次重启再算一遍。现在结论落成一个空文件
`_merged/<书名>.clean.nostamp`，一行 `exists()` 就省掉这半小时。

**四、真正的根子**：`preclean()` 把整本书的 PIL 图像攒在一个 list 里最后一次性存 PDF。
GB 50984 按 400dpi 渲是 3307×4678 一页 14.8 MB，161 页就是 **2.3 GB 未压缩灰度图**
常驻，外加每页 ~450 MB 的临时数组（像素 int16 + 亮度 float64 + 掩码）。
16G 的机器上 OCR 模型已经占着两三个 G，这一下直接顶进交换区——
第 6 本 SH/T 3196 掉到 45.2 s/页、GB 50984 去水印跑 34 分钟，都是它。
不在交换区里的时候这一步其实很快：实测一页 400dpi 渲染 0.14 s + 判色 0.55 s，
161 页两分钟就该完。**慢的不是算，是换页。**

改成逐页处理：每页判完色就压成 JPEG 塞进一个 `fitz` 文档，内存里永远只有当前一页。
改动验证过三点（`tools/test_preclean.py`，造了一本 12 页 400dpi 的假扫描书对照旧写法）：

- 每页图像流**逐字节相同**——Pillow 的 PDF 插件内部就是用默认参数存 JPEG，
  新代码直接调同一个编码器，产物和以前两本已处理的 SH/T 一模一样。
- 页面尺寸改为**取原件的 `page.rect`**，不再是「像素数 ÷ 300」。旧写法对 400dpi
  的扫描件会把页面放大三分之一（595×842 pt 变成 794×1122），只是至今没碰上：
  已处理的 SH/T 3196、3017 都是 300dpi 原扫，所以产物没变化。
- 「不足 10% 页面盖章 → 返回原件 + 留 `.nostamp`」这条路没动。

顺手否掉一条：先用 100dpi 粗判全书有没有章、有章再全分辨率重渲。
实测 100dpi 一页只省 0.6 s，一档剩下 1,600 页合计 16 分钟，
而粗判和精判的彩色占比在 2% 阈值附近可能给出不同结论——为 16 分钟改判据不值。

这几处**下次重启才生效**。正在跑的进程用的还是旧 `preclean`，一档剩下的书里
只有 SH/T 3047（36 页，0.5 GB）会走那条路，扛得住，不必为它中断第 8 本。

**五、跑久了还是会越来越慢，得定期重启**（09-22 早上确认）。
重启后 8 本跑得很正常：13.1 / 12.4 / 7.6 / 14.5 / 17.9 / 15.7 / 21.4 / 8.5 s/页。
到第 16 本（GB/T 50001，84 页）掉到 **143 s/页**——3 小时 20 分还没跑完。
当时进程内存足迹 **45 GB**（物理内存 16 GB，交换区 18.3G/19.5G 顶满），
而 RSS 只有 3.1 GB：`_reclaim()` 压得住常驻部分，压不住这个总量。

这不是 `preclean` 那个坑（那本有 `.nostamp`，几秒就过了），是进程跑了 16 本之后
自身的累积。没有继续查是哪一层泄的——**重启一次就解决，而重启现在很便宜**：
已完成的本子几秒钟跳过。与其花几小时定位一个每天只犯一次的泄漏，
不如每跑十来本重启一下。命令见待办 11。

### 3.1e 解析范围收窄到 `建筑规范/标准库/`（09-22 定）

### 3.2 去水印 — 决定 OCR 成败的一步

同一本 SH/T 3017-2013 里，没盖章的第 5 页识别得一字不差，盖了章的第 6 页：

| | 原文 | OCR |
|---|---|---|
| 条号 | 4.3 | **1.3** |
| 引用 | GB50016《建筑设计防火规范》 | GB50016《建筑设计防规范》 |
| 整条 | 4.5.2 … | **整条消失** |
| 列项 | a) b) c) d) e) | 只剩残句 |

不是模型不行，是输入被污染了。印章是绿色的、正文是中性灰黑，按
「饱和度 > 30 且亮度 > 80」把像素涂白即可，压在印章下面的笔画因为足够暗会保留。
28 页里 11 页有章，处理后上表的四类错误全部消失。

判据做了两道保险：整页彩色像素超过 2% 才算「盖了章」；全书不到 10% 的页面中招，
就当是插图，不重排。

### 3.3 切条 — 复用同一条流水线

`chunker.build_from_mineru()` 只是把 `content_list.json` 适配成
`(kind, obj, text)` 块序列，**切条规则一条没改**。
`src/batch.py` 加了 `--ocr-dir`：没有 Word 源的规范自动走 OCR 这条路。

最小单元 SH/T 3017-2013（28 页扫描件）实测：

| 指标 | 结果 |
|---|---|
| 切出 | 101 块，检索池 80 |
| 正文游离 | 0 段（0.0%） |
| 缺页码 | 0 条 |
| 章节路径修正 | 1 条 |
| 附表 | 3 张，表 4.5.4 与条文 4.5.4 同块 |
| 强条 | 0 条（依据：推荐性标准，无强制性条文） |

检索验证：`SH/T 3017 4.5.4` → 条号直达该条并带出附表；
`厂房泄压设施宜优先采用什么` → 该本 4.5.3 排第 1，GB 50016 第 3.6.3 排第 2

### 3.3b 一档头 6 本切出来发现的三个 bug

都是 OCR 源特有的，Word 源那条路上不会出现，所以要等第一批 OCR 落地才暴露。

**① 强条漏标 —— 全库 71 条**

强条在原书里是黑体字，OCR 和 PDF→Word 都丢字重，原先只能从条文说明里
找「本条为强制性条文」的自述，覆盖不全。但**发布公告页列着权威清单**：

> 其中，第3.0.2、3.0.3、4.1.3、…、9.0.7条为强制性条文，必须严格执行。

接进去之后（`announced_mandatory()`）：

| 规范 | 原判 | 现判 | 公告独家捡回 |
|---|---:|---:|---:|
| GB 50011-2010 建筑抗震设计规范 | 4 | 55 | 51 |
| GB 50009-2012 建筑结构荷载规范 | 0 | 13 | 13 |
| GB 50067-2014 汽车库防火规范 | 0 | 25 | 3 |
| GB 50037-2013 建筑地面设计规范 | 0 | 4 | 2 |
| GB 50453-2008 | 0 | 2 | 2 |

全库 71 条强条本来会被当普通条文发出去。公告与条文说明取并集，
`mandatory_basis` 记清是谁认定的。并集是有意的：漏标一条，同事照普通条文处置；
多标一条，最坏是按更严的做——两种错不对称。

只在正文起点之前的前置区里找公告，因为条文说明里也会出现
「第X条为强制性条文」，但那多半在引用**别的规范**，照抄会把别人的强条安到自己头上。

**② 正文与条文说明整个对调**

MinerU 把页眉的规范号并进了标题块，出来是 `'GB 50067 - 2014条文说明'`，
而 `NOTES_HEAD_RE` 要求整行就是「条文说明」，于是漏判。后果不是少一个区：
条文说明把每条条号都复述一遍，条文密度比正文还高，`split_regions` 挑
「条文最密集的一段」当正文时它必胜，真正文被降级成修订区，
再被修订优先逻辑拿条文说明的文字顶掉——GB 50067 实测顶掉 75 条。
正则放开一个可选的规范号前缀即可，仍要求整行匹配（否则目次的
「条文说明……38」也会算数）。

**③ 多条挤进一个文本块**

MinerU 按版面切块，一栏文字连排下来常并成一块。GB 50067 的 p21 把
「条5.1.3第4款 + 条5.1.4 + 条5.1.5」并成一块，切条器只认行首条号，
后两条连号带页码带强条标记一起丢——**两条都是强条**。
`mdblocks.split_inline()` 按「句号后紧跟三级条号」拆，排除
「第X条」「表X」这类交叉引用；`load_page_map()` 必须用同一套拆分，
否则拆出来的条查不到页码。

**顺带做了一条常驻校验**：公告点了名、正文里却没切出来的条，每本都告警。
免费，且校验的正好是最不能丢的那部分。全库 35 本只触发一次——
GB 50011 第 3.1.1 条（强条）跟节标题「3.1 建筑抗震设防分类和设防标准」
黏在同一块里，条号成了「3.1」。文字没丢，但查不到条号、标不上强条。
没动 Word 路径的切分逻辑：那条路上 GB 50016 的结果是验过的，
不值当为一条冒险，留给人工。

### 3.3c 补切 OCR 积压的 16 本，顺手挖出一个静默吞书的 bug（09-22）

原料和成品差得太远：Word/MinerU/OCR 三路原料九十来本，`data/chunks` 只有 35 本。
切条不费 GPU，和 OCR 并行跑不冲突，于是先把这个洞补了。

只切「本机 OCR 有产物、且还没入库」的 16 本，纯增量。挑这批的理由：
它们全部来自 `建筑规范/标准库/` 的 PDF，符合 3.1e 的新范围，
而且事先验过这 16 本**一本都没有 Word 源**——否则 `batch.py` 会优先走 Word 路径，
等于绕过新范围偷偷用了 `建筑规范/word` 里的文件。

结果 **15 本成功，1 本失败**。库从 35 本 → **50 本**，检索池 4,737 → **6,597 条**，
强条 879 → **1,398 条**（新增的 GB 55002/55016/55019/55031/55036 五本通用规范
是全文强制，109/85/97/95/92 条全部为强条，与纸面一致）。

**失败那本挖出了 `chunker.py` 的一个真 bug。** `build_dep()` 原先是双返回形态：
`quiet=True` 返回 `(chunks, diag)`，否则返回裸 `chunks`。而
`build_from_mineru()` 第 839 行写的是 `build_dep(blocks, meta)[0]`——
非 quiet 调用，拿到的是裸 list，`[0]` 取的是**第一个 Chunk**。

也就是说：任何走这条路的书都会被**悄悄削成一块**，全书只剩第一条。
它没造成脏数据纯属运气——第一本走到这条路的书正好切出 0 条，于是
`IndexError` 炸了出来，而不是安静地写进一个只有一条的 jsonl。
查过全库 50 个文件，**没有块数 ≤1 的，历史数据干净**。

修法不是给那一行打补丁，是把双返回形态拆掉：`build_dep` 现在**永远**返回
`(chunks, diag)`，`quiet` 只管要不要打印。三个调用点统一加 `[0]`。
回归：13 本企标（Word 源）重切一遍，块数与修复前**逐本一致**。

**剩下的真问题：`SH/T 3196-2017` 用的是两级条号。** 4.1 / 4.2 / … / 4.12 这种
GB/T 1.1 写法，而 `CLAUSE_RE` 是**故意**不认两级编号的
（实测两级命中全是目次行和公式残片）。于是它既进不了正文路径，
`depdoc` 又找不出企标结构，切出 0 条。OCR 产物本身是好的
（153 块 / 6,961 字 / 28 个表），不是识别问题，是体例问题。

已 OCR 的 24 本里**只有这 1 本**是两级体例，所以先记下不做。
真要做，得给 `chunker` 加一条「两级条号」路径，且必须能和目次交叉验证，
否则会把目次行当条文切进去——那比少一本书糟得多。

### 3.3d 一档跑完，补切收尾，又捞出两个「静悄悄」的坑（09-22 22:30）

一档 **26/26 全部完成**：636 页 / 169 分钟 / 均速 **15.5 s/页**。
重启前那两本是 59.4 和 171.1 s/页，差四到十倍，全是内存换页吃掉的。

新增 `tools/chunk_new.py`：把「OCR 跑完但没入库」的书找出来补切，
并**硬性剔掉有 Word 源的书**（那些 Word 在 `建筑规范/word`，属 3.1e 范围外；
`src.batch` 有 Word 就优先走 Word，不剔等于范围收窄悄悄失效）。
支持 `--wait-pid`，挂着等 OCR 退出再自动切；等超时会报警而不是在半截产物上切。

收尾补切 5 本，**成功 4 本**（Q/SH 0705、GB 50896、GBZ 1、SH/T 3219）。
库：**59 本 / 11,753 块 / 检索池 7,710 条 / 强条 1,401 条 / 带表 684 条**。

**坑一：3.3c 那个修复把崩溃变成了空文件。** `build_dep` 修好之后不再抛
`IndexError`，改为老老实实返回 `[]`，于是 20:13 那次全量切条给
`SH/T 3196-2017` 写了一个 **0 行的 jsonl**。这比崩溃更坏：
`batch` / `tools.queue` / `tools.chunk_new` 都靠 glob 认「已入库」，
看到文件就不再排它——库里就多了一本**查得到书名、查不到条文**的规范，
而且没人会发现。已删除该空文件，并在 `batch.py` 写盘处加了拦截：
切出 0 条就不写文件，计入 skipped 并打印原因。

**坑二：`depdoc._numpr` 对 OCR 源直接崩。** `Q/SH 0841-2022` 报
`'NoneType' object has no attribute '_p'`。根因是那行
`numbered = bool(inline_no) if inline else _numpr(obj) is not None`——
`_numpr` 读的是 Word 的自动编号元数据（`w:numPr`），而 OCR 产物的 `obj` 是 `None`。
自动编号是排版元数据，OCR 里根本不存在，**返回 None 才是实话，抛异常是把
「恢复不了条号」伪装成了故障**。已加 `p is None` 守卫。
同时 `build_from_mineru` 在企标路径切出 0 条时改为抛带诊断的 `ValueError`，
说清是「疑为 GB/T 1.1 两级体例」，而不是返回空列表让上游去猜。

**剩两本卡在同一个体例问题上**，现在报错干净、留在待办里，不会伪装成已完成：

| 规范 | 体例 | OCR 产物 |
|---|---|---|
| SH/T 3196-2017 石油化工企业建筑物分类标准 | 两级（4.1…4.12） | 好：153 块 / 6,961 字 / 28 表 |
| Q/SH 0841-2022 建筑抗台风设计规定 | 两级（4.1 / 5.1 / 7.1） | 好：38 块 / 2,753 字 |

两本的 OCR 都是好的，纯粹是 `CLAUSE_RE` **故意**不认两级编号
（实测两级命中全是目次行和公式残片）。要不要给切条器加两级路径，待定。
`python -m tools.chunk_new` 任何时候都会把这两本列出来提醒。

回归：13 本企标（Word 源）两次修改后各重切一遍，块数逐本一致；全库 0 个空文件。

### 3.3e 两级条号体例（GB/T 1.1）：目次当判据（09-22 定，已落地）

3.3d 卡住的两本（SH/T 3196-2017、Q/SH 0841-2022）用的是 GB/T 1.1 体例，
条号只写到两级（4.1 / 7.13）。国标路径的 `CLAUSE_RE` **故意**拒绝两级——
放行以后命中的全是目次行和公式残片，会往检索池注入几百条假条文，那条拒绝不能松。
所以另开一条路径 `src/twolevel.py`，**必须能和目次交叉验证**（用户要求）。

**核心做法是把扫描反过来。** 不是「扫出所有像条号的东西再过滤」，
而是「按目次，我知道下一个该是谁，去正文里找它」。这一反转带来三件事：

| 难点 | 自由扫描 | 按目次找 |
|---|---|---|
| 交叉引用「符合第4.1 条规定」 | 切成新条 | 当时期望的是 5.1.1/5.2/6，「4.1」不在其中 → 不动 |
| 目次页码粘连「…296.1建筑热工节能设计」 | 读成「96.1」 | 直接找「6.1」，一击即中 |
| 条与款的分界 | 只能写死 | 问目次：0841 目次只列到章 → 4.1 是**条**、5.1.1 是**款**；<br>3196 目次列了 6.1/6.2/6.3 → 那是**节**，条落在 6.1.1 |

第三行是这条路径最值钱的地方：同样是「X.Y」，两本书里的身份不同，
不写死、问目次就对了。条 5.1 的正文是「下列地区内的建筑应进行抗台风设计：」，
把款摘走只剩一个冒号，检索到它等于什么都没查到。

**章节标题必须编号和标题都对得上目次**（`_heading_at`），
光对编号不够——正文里一句「4 抗震设防烈度为6度」和章标题在字面上无法区分。

**对不上就拒绝出货。** `diag["trusted"]` 要求：目次≥3 章、正文按**原序**命中
≥80% 的章、切出≥10 条。不通过就抛 `ValueError`，不降级、不「尽力而为」。
理由同 3.3d：库里多一本条号错乱的规范，比缺这本书糟得多。

**落地过程中打掉的两个错**（都是先切出来看、再对着原文查出来的）：

1. `见表5.1。` 被切成了条 5.1。这个「5.1」**恰好就是**当时期望的下一条条号，
   期望集合挡不住。加了一对引用前后缀（`_REF_LEAD` / `_REF_TAIL`，
   挡「第/表/图/式/见/按」和「条/款/项」）才修掉。
   不修的后果是 SH/T 3196 第 5 章的 25 页大表整个挂到一条不存在的条上。
2. 条文说明区自带第二份目次（「3术语 …36」），编号标题都跟正文目次对得上，
   被当成章标题吃了进去，真章标题排在后面反而追不上。按行尾页码识别并跳过。

**结果**：

| 规范 | 章 | 条 | 块 | 正文游离 | 页码 |
|---|---|---|---|---|---|
| Q/SH 0841-2022 建筑抗台风设计规定 | 8/8 | 38 | 41 | **0 字** | 全有 |
| SH/T 3196-2017 石油化工企业建筑物分类标准 | 6/6 | 22 | 44（含条文说明 16） | **0 字** | 全有 |

页码直接从 `content_list.json` 的 `page_idx` 带过来，不走
`load_page_map` 的条号反查——本路径会把并排的多条从同一块里切开，
切出来的条在原文里没有独立起始行，反查必然落空。

**回归**：全库重切一遍，59 个旧 jsonl **逐字节一致**，只多出这两本。

### 3.3f 向量与重排改在本机跑，只有作答还要 key（09-23 定，已落地）

用户问「向量和重排你不能做吗」，问到了点子上：这两步本来就是**跑模型**，
不是**问模型**，没有非用云端不可的理由。于是改成：

| 环节 | 之前 | 现在 | 要 key 吗 |
|---|---|---|---|
| 向量化 | 硅基流动 API | 本机 `bge-m3`（1024 维） | 不要 |
| 重排 | 硅基流动 API | 本机 `bge-reranker-v2-m3` | 不要 |
| 作答 | DeepSeek | DeepSeek（不变） | **要** |

这不只是省一个 key。**条文正文不再离开这台机器**——出网的只剩最后一步
把选中的几条送去总结，范围小得多，也好解释。云端那条路原样留着
（`KB_EMBED_PROVIDER=siliconflow` 可切回），因为本机推理是单机串行的，
真上了多人并发未必扛得住；切回去需要**同时**填 key 和写环境变量，
分两步是故意的：条文出不出网，得是明写的决定，不能靠忘了填 key 来保证。

模型用 `tools/get_models.py` 从 ModelScope 下到 `kb/models/`（一次性，共 4.6 GB）。
直接用 `transformers`，没装 sentence-transformers / FlagEmbedding——
这个 conda 环境是 magic-pdf 在用的，装新包有把 OCR 搞坏的风险，
而且里头的 sentence-transformers 本来就已经是坏的。

**实测确认**（不是看文档推的）：

- 向量：「疏散楼梯的净宽度」vs「楼梯间要多宽」余弦 **0.78**，
  vs「消防车道的宽度」0.63，vs「外墙保温燃烧性能」0.45。
  头两句一个字都不重合，BM25 必然漏，向量能捞回来——这正是当初要向量的理由。
- 重排：正确条文 +3.26，其余全为负，差距悬殊。

**建索引时踩的坑（16 GB 机器的现实）**：

- 头一次跑到 1344/7678 就 MPS OOM。报的是「我们自己占 2.96 GB，
  其他占 17.10 GB」——不是我们吃多了，是没给别人留余地。
- 四处改动，都在 `providers.py`：**fp16**（权重 2.3 GB → 1.15 GB；
  实测与 fp32 的向量余弦 0.999999，排序看不出差别）、
  **按 token 预算分批**而不是固定条数（注意力开销是 批大小 × 长度²，
  检索池里绝大多数条文很短，但有那条塞着 25 页大表的；固定分批就得
  按最坏情况留显存）、**OOM 时对半拆批重试**、**拆到底还不行就整体退到 CPU**。
- 最后那条才是真正解决问题的。前三条做完，占用从 2.96 GB 降到 1.16 GB，
  **还是 OOM**——报的是 other allocations 19.51 GiB、连 2 KiB 都分不出来。
  说明瓶颈根本不在我们这边：16 GB 的机器上同时开着编辑器和浏览器，
  MPS 的水位线算上压缩内存就已经满了。这种情况下继续拆批是徒劳的，
  只会把失败推迟几秒。退到 CPU 慢 6 倍（实测 630 ms/条，全库约 50 分钟），
  但内存有上界、一定跑得完。建索引是一次性的事，宁可慢一趟，
  也不要跑了半小时再炸——炸了还得增量续跑，反复几轮比一次跑完更慢。
- 顺带一个教训：头一次跑我把输出接了 `| tail`，**退出码变成了 tail 的 0**，
  失败看起来像成功。查这类长任务，管道要么别接，要么单独看退出码。

**索引建成后的实测**（`data/chroma`，7,678 条）。`[向量+重排]` 这个标记
表示 BM25 一条都没捞到、全靠语义命中——正是当初要上向量的那类问题：

| 大白话提问 | 命中 | 路径 |
|---|---|---|
| 楼梯间要多宽 | GB 50016 第5.5.18条「疏散楼梯的净宽度不应小于1.10m」 | BM25+向量+重排 |
| 残疾人坡道最陡能做到多少 | GB 50763 第3.4.4条「轮椅坡道的最大高度和水平长度」 | **向量+重排** |
| 厂房里放易燃品的地方离办公室要隔多远 | GB 50016 第3.4.2条「甲类厂房与重要公共建筑的防火间距不应小于50m」 | **向量+重排** |

「残疾人」对「轮椅」、「最陡」对「坡度」、「易燃品」对「甲类」、「隔多远」对
「防火间距」——一个字都不重合，BM25 必然漏。

条号直达同时回归过一遍，5 条全中（SH/T 3196、Q/SH 0841、Q/SH 0705、
GB 50016、GB 50763），且「坡度 6.5% 怎么处理」仍然不误判为条号。

### 3.3g 建索引时撞出来的两个切条 bug（09-23）

都是 Chroma 报「chunk_id 重复」才暴露的，此前静悄悄躺在库里。

**一、GB 50763 的条文说明整本被当成了正文。** 89 条解释性文字顶着条号
混在检索池里——「本条规定了制定本规范的目的」这种话会被当成条文原文答出去，
这比查不到更糟。根子是条文说明扉页那一块：整页只有规范名、规范号、
「条文说明」三行，MinerU 并成一块、`tidy` 再把换行压成空格，成了
`'无障碍设计规范 GB 50763 - 2012 条文说明'`，而 `NOTES_HEAD_RE` 只兜了
「规范号 + 条文说明」，没兜规范名。补上规范名那一段即可。
修完这本检索池 286 → 185，顺带「修正章节路径」从 97 条掉到 2 条——
那 97 条本来就是在给错标的条文说明修路径。全库重切，**只有这一本变了**。

**二、没有条号的企标会撞 id。** DEP 的术语表整章没有条号，每段都落在
`#正文#5` 上。这些段落内容各不相同，不能合并，只能让 id 唯一。
修在 `batch.py` 写盘前而不是各切条路径里：chunk_id 唯一是**写盘时的不变量**，
三条路径各保证一次，早晚会漏掉第四条。全库 11843 块，现在重复 id 为 0。

### 3.3h 二档入库前的三处切条修补（09-24）

每处修完都全库重切，和修之前的快照逐本、逐条比对（条号、区段、页码、正文），
只接受「预期内的那几本变了、其余一个字节不变、没有一条正文条号消失」。

**一、混合体例。** SH/T 3103 第 5、11 章是三四级条号，第 4、6～10 章是两级，
三级路径只切得开前者，后者整章打成一块。现在 `build_from_mineru` 发现有
整章打包（`packed_chapters`：块的条号是纯章号、块里却有 ≥2 个行首「N.k 标题」）
就改试 `twolevel`。两级路径同步改了两处：条的层级由正文决定
（`_clause_candidates`：下一级 / 同级 +1 / 回退到上级，不越过节），
只有标题的父条并进子条的章节路径（`_fold_title_clauses`）。

第一次全库重切，GBZ 1 和 GB 8624 **退步**了：GBZ 1 的「6 工作场所基本卫生要求」
被 OCR 粘在上一段句尾，两级路径认不到第 6 章，整章并进 5.3.6（一块 7,504 字）；
GB 8624 的附录 A、B 共 14 条并进了第 7 章。两本都过了两级路径自己的「可信」
检查——那道检查允许漏两成的章，是给「只有这条路」的书留的余地。
拿它去**替换**一个能用的结果，标准得更严，于是加了一道闸（`uncovered`）：
**三级路径能单独查到的条，两级路径一条都不许丢**（子条还在的只有标题父条不算丢）。
结果：Q/SH 0841、SH/T 3103（正文 48→114）、SH/T 3219（74→146）换过去；
GB 8624、GBZ 1、SH/T 3014、3017、3047、3206 被拦回三级路径结果。
SH/T 3047 两级路径能多切出约 80 条、只丢 3 条（其一是 OCR 垃圾 `7.3.5.260`），
严格闸门下也没换——宁可保守，以后要放宽再按本看。

**二、书末附件。** 「本规范用词说明」「引用标准名录」粘在最后一条的尾巴上，
35 本里有 33 本仍在（`cut_back_matter`，在 `batch.py` 统一截）。

**三、通用规范（GB 55xxx）的起草说明。** 通用规范正文之后是
「起草说明 → 一、基本情况 → 二、起草人员 → 三、术语 → 四、条文说明」，
分区只认最后一个「条文说明」标题，前三节全落进正文：术语表按
「1 砌体结构」「2 无筋砌体结构」切成几十个假条（GB 55007 有 24 个），
**而且因为通用规范全文强制，都被标成了强条**；没切成假条的，就粘在最后
一条后面（GB 55001 一块 4,963 字）。修法：先照旧定正文，再把正文之后的
第一个「起草说明」或**重复封面**「中华人民共和国××标准」当说明区起点
（`draft_start`，Word 和 OCR 两条路径同一判据）。重复封面这一条顺带救了
SH/T 3206：它的 OCR 丢了「条文说明」四个字，整份条文说明
（「11.1.1 条文所列出的设计文件仅为…」）原本全在正文里。
15 本通用规范变了，其中 6 本（55002/55015/55016/55019/55031/55036）是
早就入了向量库的 Word 源——线上检索此前一直带着这些尾巴。

### 3.3i 三档入库：两个静默错误（09-25）

三档 42 本全部切通，老的 117 本一个字节未变。逐本过数时抓到两个问题，
都是「不报错、结果却错」那一类。

**一、公告强条清单遇括号即失效。** `ANNOUNCE_RE` 只认「数字、点、顿号」，

碰到第一个括号正则就匹配失败，整张清单返回空集，强条只剩条文说明自述的那部分，
**不报任何警告**。修后全库重切，**只有强条字段变了**，21 本补上强条共 240 条：
GB 50160（0→56）、GB 50074（0→29）、GB 50183（0→33）、GB 50098（0→18）、
GB 50737（0→13）、GB 50574（0→11）、GB 50003（4→13）、GB 50030（19→30）等。
GB 50160 是一开始就入库的核心规范，此前检索时它的强条一条都不带【强条】标记。

公告列了、正文里却没有单独成块的强条，有 8 本共 16 条（批跑日志里「公告列为强条、
但正文里没切出来」）。查过的几条都是 OCR 把两条粘成一段（GB 50108 的 4.1.26
并在 4.1.25 里），**文字查得到，但不带条号、不标强条**。见待办 14。

**二、整本与分册同时在库，被拼成了两遍。** 标准库里 GB 50074 既有整本，
又有 `_部分1/_部分2`，`group_parts` 把三份拼成一本 384 页上云。后一遍被切条器
认成「局部修订区」，**正文 420 条全被判为已被取代**。修法：同组里有整本就只用整本
（`src/ocr.py`）。已有产物不必重跑：拼合时整本排第一，前 192 页正好就是整本的结果，
截掉后半即可（原件留在 `*_content_list.dup384.json`）。二、三档清单里只有这一本。

**顺带修的：云端上传失败的段永远补不回来。** 重跑时 `ocr_cloud.py` 把 manifest 里有记录的书
一律视为已提交，失败的段不会重传；而轮询又会把「上传失败」覆盖成云端报的 `waiting-file`，
主循环永远等不完。现在重跑只重传失败的段（本次 4 段 663 页，3 分钟补齐）。

### 3.5 台账里发现的数据问题

三条编号/名称矛盾已逐一翻原件核实并订正，结论如下。

| 问题 | 核实结果 | 处理 |
|---|---|---|
| `GB 50033-2013` 与 `GB 50037-2013` 文件名都叫「建筑地面设计规范」 | 翻封面：GB 50033 那份印的是《建筑采光设计标准》，**编号对、文件名错**；GB 50037 确为《建筑地面设计规范》 | `overrides.tsv` 订正名称，源文件不动 |
| `GB/T 50011-2010 建筑抗震设计标准` 只有 20 页，且 GB 50011 不是推荐性标准 | 确是《建筑抗震设计规范》GB 50011-2010(2016年版) 的**局部修订条文（2024年版）**，比库里的 2016 版新 | 编号订正为 `GB 50011-2010（2024年局部修订）`，档位标 `-` 不入库；涉及的条文挂提醒（见下） |
| `SH/T 3006-2012` 已被 2024 版取代 | 属实，2024 版已在库 | 档位表 `-`，不入库 |

还剩两条需人工：11 个内容重复组要过一遍台账；3 个打不开的文件需重新取得，
其中 `GB/T 50779-2022 石油化工建筑物抗爆设计标准` 是一档规范，缺它影响较大。

#### 订正不改源文件：`data/overrides.tsv`

台账的编号和名称全靠文件名推断，而文件名是会错的。直接改用户的源文件，
等于把「文件名错了」这件事抹掉——下次重扫台账，没人记得为什么这本叫这个名。
所以订正单独记一张表（`文件名 → 要覆盖的字段`），`src.catalog` 重扫时自动套用，
并打印「人工订正 N」。表里有条目匹配不上文件时**大声报错**，
因为一条悄悄失效的订正比没订正更危险。

#### 引用提醒：`data/clause_notes.tsv` + `Chunk.caveat`

GB 50011 的 2024 局部修订件**没法自动入库**：那份 PDF 用下划线表示新增、
方框表示删除，是纯视觉标记，OCR 认不出来，抽出的文字新旧混在一起
（3.10.2 抽出来是「…的性能目标。的性能目标。建筑的性能目标，宜采用…」）。
塞一段读不通的文本进库比不入库更坏。

但库里那 9 条 2016 年版的原文仍然查得到，**看不出它已经被修订**——这才是真风险。
于是加了第三种状态：

| 字段 | 含义 | 对检索的影响 |
|---|---|---|
| `status` | 现行 / 废止 | 仅展示 |
| `superseded` | 库内另有更新版本顶上 | **踢出检索池** |
| `caveat` | 这条抄得没错，但引用前必须知道一件事 | 仍可检索，但**强制随条文一起显示** |

`caveat` 在检索结果里顶格标 `⚠`，在问答里作为【引用提醒】进上下文，
并由 SYSTEM 铁律第 7 条要求模型原样转达。切条时按 `(规范号, 条号)` 自动挂载，
挂不上的条号会逐条报出来。

已挂 8 条（3.9.2、3.10.1–3.10.5、5.4.1、12.1.6）。
**第 9 条 3.1.3 挂不上，也查不到**——它是 2024 年新增条文，2016 年版正文里没有这一条，
没有可挂载的基条。这是目前已知的唯一知识盲点，见待办 9。
